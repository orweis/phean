## Working on Phean

Read [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) first. The rules below are the ones that are easy to break.

### Commands

- `pnpm check` (typecheck, lint, tests) must pass before every commit. Run `pnpm build` too when touching routes, layouts, or anything imported at module load.
- `pnpm test:e2e` builds and runs the Playwright UI tests on port 3200 against `.data/e2e`. Run it after any UI change. It needs `pnpm exec playwright install chromium` once, and it reuses a server already listening on 3200, so stop a stale one after rebuilding. `E2E_PORT=3300` runs it on another port, so two checkouts can test at once. To rerun without rebuilding: `pnpm exec playwright test`.
- CI (`.github/workflows/ci.yml`) runs `pnpm check` and `pnpm test:e2e` on every pull request.
- Work that needs direct access the cloud session lacks (the Vercel dashboard or CLI, a store's token, production secrets) is spun off as a local session on the owner's machine with a self-contained prompt, rather than handed back as manual steps. Never paste tokens or secrets into a chat, a prompt, or the repository.
- `pnpm dev` and `pnpm db:seed` both use the on-disk PGlite database by default, and PGlite allows one process at a time. Stop the dev server before seeding.
- `PageProps<"/route">` and `LayoutProps<"/route">` are generated types. `pnpm typecheck` runs `next typegen` first, so a fresh checkout has them; a bare `tsc` will not.

### Where code goes

- Business rules live in `src/server/domain` as `service(schema, run)` functions, which validate their own input. Routes, server actions, and MCP tools are thin adapters that take the service itself; they never query the database themselves. Nothing in `src/app`, `src/components` or `src/lib` imports `@/server/db`, `drizzle-orm` or a database driver (ESLint refuses it): a page or route that needs the database without a workspace context calls a bound entry point in `src/server/entry.ts`, or `ownMemberships`/`personContext` in `server/auth/session.ts`.
- Tenant scoping comes only from `Ctx`, which is built from a session or from the verified agent's row in `agents`. Every query on a tenant table filters through `inTenant(ctx, table)` or `tenantRow(ctx, table, id)`, and every insert sets `tenantId` from `ctx` (the backoffice's cross-tenant reads are the one documented exception; see Backoffice). Never accept a tenant id or slug from tool input, and never from an OAuth token's claims: the token names only the agent (`agent_id`), and the row says which workspace it is in.
- An agent's bearer is an OAuth access token (the main path, verified by `verifyOAuthToken`, then `resolveOAuthAgent`) or a fixed `phn_` key (`authenticateAgentToken`). Every path that turns a credential into an agent goes through `resolvePrincipal` in `domain/agents.ts`, which reads the row through `liveAgent()` (`agent-liveness.ts`), so revoking, expiry and an approver leaving cut an agent off on its next request. A sub-agent is live only while its parent is, and its effective level is the lowest of its own, its parent's, and (for an OAuth agent) what its approver can grant now. Add any new token path there, never beside it.
- People sign in with a password, GitHub or Google, connected to one account from `/account` (Better Auth's account linking), and may turn on two-factor (its `twoFactor` plugin, TOTP with backup codes). The plugin only challenges a password sign-in; `providerSignInChallenge` in `server/auth/two-factor.ts` gives a provider callback the same challenge through the plugin's own cookie and verify endpoints. Any new way for a person to sign in must end in that challenge too. The desktop app's browser handoff (`nativeSignIn` in `server/auth/native.ts`) mints its session only from a full session in the browser, so it inherits the challenge; keep it that way, and keep it to `docs/apps/CONTRACTS.md`. Password lengths are `LIMITS.passwordMin`/`passwordMax`, and auth error codes become words through `authErrorMessage` in `lib/auth-errors.ts`.
- Agent levels are `read`, `write` and `admin`, the roles `agent_read`, `agent_write` and `agent_admin` in `policy.ts`. Fixed keys are Write and never expire; OAuth agents get a level and a lifetime from `AGENT_LIFETIME_DAYS` in the dialog, and there is no "never". People approve agents with `agent:connect` (Admin only with `agent:manage`; `grantableLevels` reads it from the matrix), and only owners and admins issue fixed keys with `agent:issue_key`. `agent:manage` means revoking others' agents and an Admin agent holds it; issuing keys and `member:manage` stay with people. A person may also revoke an agent they approved (`createdByUserId`), or a sub-agent of one; `canRevoke` in `agents.ts` is that rule for the service and the Agents page alike. An MCP tool for Admin agents only is `adminOnly`.
- Update services build their `set` with `patchOf`, so `undefined` means "leave it" and `null` means "clear it" everywhere, and throw `invalid` when nothing would change.
- Authorization is the matrix in `src/lib/permissions.ts` (plain data, so client-safe code such as `grantableLevels` reads the same table), enforced by `assertCan` in `src/server/domain/policy.ts`. Call `assertCan` in the service; do not scatter role checks in UI or adapters. `goal:decide` stays human-only.
- An MCP tool that is one service is `serviceTool({ name, title, description, service, key })` in `src/server/mcp/tools.ts`; use `defineTool` only when the tool adds links or formats text. Mark read-only tools `readOnly` and deleting tools `destructive`, and write descriptions for the agent that will read them.
- New workspace mutations are one `tenantAction(service, options)` line in `src/app/w/[slug]/actions.ts`, rendered with `ActionForm`, or `ActionButton` for a one-click post of fixed fields.
- Labels and colors for statuses, priorities, roles, and kinds come from the `{ label, tone }` tables in `src/lib/domain.ts`. Paths come from `routes` in `src/lib/routes.ts`. Field limits come from `LIMITS` and the slug rule from `WORKSPACE_SLUG_PATTERN`, for the schema and the form alike. Do not hard-code any of them.
- Dates are UTC calendar days through `src/lib/dates.ts` (`isoDayFromToday`, `daysBetween`, `isPastDue`), in the app, the scripts, and the tests.
- `src/lib` is client-safe and must not import from `src/server`.
- Agent sessions and questions are JSONB on `tasks`, shaped by `src/lib/agent-sessions.ts`. Change them inside `inTransaction` on a row read with `findTask(tx, id, { lock: true })`, so concurrent agents never drop each other's sessions. A session URL is checked with `isResumeUrl` in its schema and stored normalized; anything rendered as a link from agent input goes through `OutsideLink`, and only `webUrl` decides what is a web link. Never widen `RESUME_URL_SCHEMES` to schemes that run code (`javascript:`, `data:`, `file:`).
- A service that ends a task's run (complete, release, any status change except to in progress) closes its `inputRequest` with `closeOpenRequest()`, which archives it in `inputAnswers`, so no question outlives the work it was about and the Decisions page keeps its history.
- Links agents leave (`tasks.links`, `InputRequest.links`) are validated by `LinkInput` with `isResumeUrl` and stored normalized by `normalizeLinks`; render them with `TaskLinks`, which goes through `OutsideLink`.
- A task's operator is `claimed_by_agent_id` (an agent's claim) or `operator_user_id` (a person who took it), never both; `delegation` is the handover around them (`DELEGATION_STATES` in `lib/domain.ts`). Change them only through `claimTask`, `takeTask`, `handOffTask`, `cancelHandOff`, `releaseTask`, `completeTask` and `updateTask` in `tasks.ts`, which keep the two consistent; an agent must not change work another operator holds (`assertNotClaimedByOther`), unless it is being handed to it. Show them with `TaskMeta` and `DelegationBadge`.
- Subtasks are one level deep: `assertValidParent` in `tasks.ts` refuses a subtask as a parent and a task with subtasks as a child. `TaskView` carries `parentTitle`, `subtaskCount` and `subtasksDone` from `selectTaskViews`; build task lists from it, not from raw rows.
- `skills/phean-decisions/SKILL.md` is the installable skill for agents that ask people for decisions. Keep it in step with "Asking the human" in `src/server/mcp/guidance.ts` and with `AskInput`; `tests/skills.test.ts` checks its tool names, kinds, fields, limits, and its example request against the server.
- `skills/phean-handoffs/SKILL.md` teaches agents operators, delegation and handoffs. Keep it in step with "Operators and handoffs" in `guidance.ts`, `HandOffInput` and `DELEGATION_STATES`; `tests/skills.test.ts` checks its tool names, states, fields and its example handoff.
- `skills/phean-webhooks/SKILL.md` teaches bots to verify and handle webhooks. When signing, headers, limits, backoff or delivery reasons change in `src/server/webhooks`, update it; `tests/skills.test.ts` runs its Node and Python verifiers against `signPayload` and checks the limits it quotes.
- Webhooks hang off `recordEvents`: it records the acting agent's watches and queues `webhook_deliveries` in the caller's transaction, and wakes the dispatcher with `onCommit`. Log every change through `recordEvents` inside the service's `inTransaction`, never by inserting into `events` directly, or bots will not hear about it. Payloads carry the event, not the object, so put what a bot needs to act in the event's `data` (ids, `goalId`, `taskId`), never secrets.
- MCP is served at `/mcp` and at each workspace's own `/mcp/w/[slug]` (`routes.mcp(slug)`), because Cursor and VS Code keep one login per URL. The slug never chooses the tenant: the handler refuses any credential whose agent works elsewhere, a workspace URL's tokens carry it as their audience, and `customAccessTokenClaims` refuses one to an agent of another workspace.
- Anything that calls an agent-supplied URL goes through `assertWebhookUrlSafe` and `postSigned` in `src/server/webhooks`; never `fetch` one directly. A Claude Code routine's Fire URL is a webhook like any other: `postSigned` recognises it (`isRoutineFireUrl` in `webhooks/routines.ts`) and sends the `{ text }` body and beta headers it takes; keep `content/docs/claude-code.md` quoting the same values (`tests/docs.test.ts` checks them).
- Decision notifications hang off `recordEvents` too: `enqueuePushes` (`server/push/routing.ts`) queues `push_deliveries` beside the webhooks' in the same transaction, a `request` push when an agent asks (or an answer is taken back) and a `resolved` one when that request closes, and wakes the sender with `onCommit` only when it queued something. Tests stop it with `setPushScheduler`. The payload is built at send time from the task read in the tenant (`server/push/payload.ts`, CONTRACTS.md's shape, under 3 KB, minimal on a `private` device), and is never stored or logged.
- `push_devices` is person-level, like `user`: one device hears every workspace its person is a **member** of (never a platform admin's read-only ones), checked when queued and again at send time. Device services take a `PersonCtx` (`personContext`, built only from a session) through `personService`; anything an adapter knows that input must not carry (the session id) is the service's server-only second argument. `push_mutes` is a tenant table, read and written through `inTenant`. Devices end with their sessions and follow one Better Auth replaces (the `pushDeviceSessions` plugin in `auth/push-devices.ts`: its `before` hook on sign-out and every session revocation, and, for the endpoints in `SESSION_ROTATING_PATHS`, a `before` that notes the devices and an `after` that acts only if the call succeeded; add any new endpoint that rotates or ends a session there), on a password reset, and when the push service refuses them (401, 403, 404, 410, or `PUSH_MAX_FAILURES` in a row); a session's expiry does not end one. The browser ties its device to its current session on every load and forgets it by endpoint when it signs out. Moving a device to another person needs the subscription's keys, not only its endpoint.
- Posting to a push service is the one exception to the `postSigned` rule: `webPushSender` in `server/push/dispatch.ts` sends through `web-push` (VAPID, RFC 8291) after `assertPushEndpointSafe`, which allows only the browsers' push hosts (`PUSH_HOST_SUFFIXES`) and runs the webhooks' private-address check, at registration and before every send. VAPID keys come from `vapidConfig()`, read when used; without them nothing is sent.
- Answers from outside the app (a notification's button, the desktop) go through `/w/[slug]/push/answer` and `/push/undo`, which build their `Ctx` only through `requireWorkspace(slug)`, require JSON and the `Phean-Client` header, refuse a foreign `Origin`, accept a `Sec-Fetch-Site` only of `same-origin` (the page) or `none` (the desktop), and pass a request id and an option **index** (`answerFromNotification`), never a label, with the device's own `endpoint` so only the person's other devices are told. `answerInput` refuses a stale `requestId` as a conflict, so every form that answers a request posts its `requestId`. Only the person who answered takes an answer back (`answeredByUserId`).
- A task's `status` is its kind; the board's lanes are the workspace's stages (`lib/workflow.ts`, saved per workspace by `saveWorkflow`). Read a task's lane with `stageOf(workflow, task)` and its name with `stageLabel`, never `TASK_STATUS_META` alone; in server components the workflow comes from `workspaceWorkflow(slug)` in `server/web.ts`. Any service that changes a task's status clears `stage` unless it keeps the kind. Charts stay per kind.
- Document bytes go through `blobStore(ctx)` in `server/storage/blobs.ts` (private Vercel Blob, or the database), never `@vercel/blob` directly, and are served only by `/w/[slug]/documents/[id]/file` after its access check. Render agent Markdown with `MarkdownView` (no raw HTML) and HTML documents as source only. `skills/phean-documents/SKILL.md` teaches agents documents; keep it in step with "Documents" in `guidance.ts` and with `AttachDocumentInput` (`tests/skills.test.ts` checks it).
- Links to one thing in Phean come from `pathOf` in `lib/links.ts` (by id prefix) and `routes`; `/w/[slug]/link/[id]` redirects any id to its page, and the Decisions and Memory pages bring `?focus=` into view with `FocusOnLoad`. Every MCP tool result passes through `withUrls` (`mcp/links.ts`), so each task, goal, document, memory and request it returns carries an absolute `url`; give a new linkable kind a prefix there, not a link field in each tool. In the app, an item's link is `CopyLinkButton`.
- The service worker `public/sw.js` is generated by `pnpm sw` from `src/lib/service-worker.ts` and the pure `src/lib/push.ts` (never edit it by hand; `tests/service-worker.test.ts` checks it is in step and runs it in a `vm` sandbox). It handles GET page loads only, caches nothing but `/offline` and its static files, and opens only `routes.request` built from a payload's ids, per `docs/apps/CONTRACTS.md`. App pages carry the baseline CSP from `next.config.ts`; never add `form-action` to it, which breaks the OAuth dialog's redirects to clients.
- `answered` and `answered_elsewhere` are the only outcomes delivered to agents (`DELIVERED_OUTCOMES`); deliver them through `collectAnswers` so each answer arrives once.

### Backoffice

- `/admin` is Phean's own read-only console over every workspace, for platform admins only (`docs/backoffice/PLAN.md` has the metric definitions). Everyone else gets the same 404 as a missing page, the export route included (`requireBackoffice` in `server/backoffice/session.ts`); signed-out visitors are sent to sign in by the proxy first. Add new pages to `ADMIN_PAGES` and `adminPaths` in `server/backoffice/paths.ts`, and to `BACKOFFICE_PAGES` in `e2e/quality.spec.ts`.
- Backoffice reads live in `src/server/backoffice` as `platformService(action, schema, run)`: it validates, re-reads the admin's row (`assertPlatformAdmin`: a verified address in `PHEAN_PLATFORM_ADMINS`, and two-factor when `PHEAN_ADMIN_REQUIRE_2FA` is on), runs, and writes a `backoffice_audit` row with the parsed input. They take a `PlatformCtx`, built only from a session; no MCP tool, `tenantAction` or agent ever reaches one. Export each from `server/backoffice/index.ts` and give it an entry in `everyBackofficeCall` (`tests/support/backoffice.ts`), which the policy test refuses for people, agents of every level and unverified addresses.
- **The one exception to `inTenant`:** backoffice services read across tenants on purpose and so filter by no tenant. They never write tenant tables (the audit log and the usage rollup are their only writes) and never build a `Ctx`. Name every column a query reads, never `select *`, so a secret column never leaks.
- A platform admin opens a workspace they are not a member of (`/w/[slug]`) only through `platformWorkspaceAccess` in `requireWorkspace`: two-factor when required, a live content grant for it, one `view.workspace_app` audit row per grant; otherwise they are sent to its backoffice page to give a reason. Two-factor is required on every Vercel deployment; `PHEAN_ADMIN_REQUIRE_2FA=0` works only where `VERCEL_ENV` is unset. Backoffice paths live in `server/backoffice/paths.ts`, never `lib/routes.ts`, so no client bundle or the service worker names the console.
- Aggregates and metadata by default. Customer content (task titles, decision questions and answers) is read only by `getWorkspaceContent`, inside the 30-minute grant a reasoned `revealContent` records for that admin and workspace. Memories, documents and event summaries are never shown. Never show tokens or prefixes, key hashes, webhook secrets, header values or full URLs (show the host, `webhookHost`), push endpoints or keys, sessions, passwords, two-factor secrets or client addresses.
- Trends read `usage_daily` (events per day, workspace, actor and action, rolled up hourly by the pipelines tick through `rollUpUsageIfDue`, or on demand at `/api/admin/rollup`) through `usageSource`, which computes the days not stored yet live; never scan `events` per page view for history. MCP calls are counted per day by `scheduleToolCount` in `mcp/handler.ts` (`tool_calls_daily`), after the answer, never logged. Indexes the backoffice needs on busy tables (`events`, `tasks`) go in `BACKOFFICE_INDEXES` (`server/backoffice/indexes.ts`), built `CONCURRENTLY` by the cron, never in a migration, which would block the running release's writes during a deploy. Metric maths lives in `lib/backoffice.ts` with unit tests, in trailing 7-day windows (`trailingWindows`) of UTC days.

### Database

- Change the schema in `src/server/db/schema`, then `pnpm db:generate` and commit the SQL in `drizzle/`. Migrations only move forward and run on every Vercel build, so keep them compatible with the previous release.
- The public site (the landing page, `docs`, `blog`, `privacy`, `components/site` and `components/marketing`) never reads the database, so it stays up when the database is down: it asks `hasSessionCookie()` whether someone is signed in, never `getSession`. `tests/site.test.ts` checks this. The sign-in pages read the session through `getSessionIfReachable()`.
- Nothing may open the database at import time; `next build` runs without one. Use `getDb()` inside functions, or `lazyDb` where a handle must exist at module load. `auth` in `server/auth/auth.ts` is a lazy Proxy for the same reason (the OAuth provider writes its resource row when built): import it freely, but build a real instance only with `createAuth(db, baseUrl)`, as the tests and `auth.config.ts` do.

### Native apps

- The desktop (Electron) and Android (Trusted Web Activity) apps are shells around this web app, in their own repository, [orweis/phean-apps](https://github.com/orweis/phean-apps). Its `docs/PLAN.md` is the plan. This repository serves them; see [docs/apps/README.md](docs/apps/README.md).
- **Build every new surface here, never in the apps.** A page added here must appear in both apps with no app change, which is why the desktop allows navigation by origin, never by path.
- **A native capability is added only through the shared bridge**: `window.pheanDesktop`, typed in `src/lib/desktop.ts`. It is feature-detected and has a web fallback, so the same page works in a browser, on the desktop and on Android. A page learns it runs in a shell only from the bridge or from `display-mode: standalone`, and uses that only to adjust chrome. Never fork a layout per platform.
- **The 375px checks in `e2e/quality.spec.ts` are the mobile gate.** A page that passes them is the Android app's page. Respect safe-area insets and touch targets.
- **The wire contracts change only additively.** They are in [docs/apps/CONTRACTS.md](docs/apps/CONTRACTS.md): the sign-in handoff, the inbox feed, answers from notifications, and the push payload. Installed apps are older than the server. Change the contracts here first, then copy them to phean-apps, whose CI compares the two.

### UI

- [DESIGN.md](DESIGN.md) is the visual system; read its Do's and Don'ts before styling anything. Colour and shadow tokens live in `src/lib/theme-tokens.ts`, one light and one dark palette per theme, and `pnpm themes` writes them into `src/app/themes.css` (never edit that file by hand); type, radii, motion and the utilities live in `src/app/globals.css`. Keep DESIGN.md in step when you change any of them.
- Tailwind's default palette is switched off (`--color-*: initial`). Use the token names (`ink`, `muted`, `panel`, `fill`, `rule`, `accent`, `on-accent`, `signal`, `dusk`, `late`, `wait`, `move`, `arrive`, `station-*`); `bg-blue-500` will not exist. Every theme gives every token a light and a dark value, so never write a `dark:` variant, a literal colour, or a check for which theme is on; a component that looks right through the tokens looks right in every theme. A new pair a component draws goes into `TEXT` (4.5:1) or `MARKS` (3:1) in `tests/themes.test.ts`, which checks it in every theme and appearance.
- The appearance (Light, Dark, or System) is the `phean-appearance` cookie and the colour theme the `phean-theme` cookie (Dusk when unset), rendered as `<html data-appearance data-theme>` by the root layout through `getAppearance()` and `getTheme()` in `server/web.ts`; each theme's dark tokens and the custom `dark` variant key on `data-appearance`, with System following `prefers-color-scheme`. Anything that must match them on the server (the `theme-color` meta) reads both, and `lib/appearance.ts` and `lib/themes.ts` hold the values the pickers and the layout share (`themeColorFor`, `THEME_PAPER`). The pickers are `AppearancePicker` and `ThemePicker`, which apply through `components/look.ts`; never read `matchMedia` for the appearance in a component. The icons, the favicon badge and the digest email are the brand mark in fixed colours, and the two-factor QR code draws `dusk` on `dusk-ink`, which every theme keeps dark on light at 7:1.
- The brand (`accent`: periwinkle in Dusk, violet in Ledger) is one or two filled primary buttons per view, and `tinted` for an action repeated on every row. The signal (`signal`, the boulder's ember, apricot or amber by theme) is the boulder, the counts on the tab rail, the inbox, and the one call to action on a dusk band. Red is only for lateness, danger, and the now line. Status hues come from the tone tables and `components/charts/stations.ts`, never picked in a component.
- To add a theme, add its id and name to `THEMES` and `THEME_META` in `lib/themes.ts`, both palettes to `THEME_TOKENS` in `lib/theme-tokens.ts` (every token), run `pnpm themes`, set its `THEME_PAPER`, and make `pnpm test` pass: `tests/themes.test.ts` checks the stylesheet is in sync and every pair's contrast, that `late` stays red and `signal` warm, that the stations stay apart, and that the QR code stays dark on light. `e2e/quality.spec.ts` then scans the key pages in it in both appearances, and DESIGN.md's Themes table gets its row.
- Liquid Glass belongs to the functional layer only: `glass-bar` for the sticky header and `glass-float` for menus, popovers and sheets. Never make a card, lane or chart glass. Controls are capsules (`rounded-full`); cards are `rounded-lg`.
- Three weights only: `font-normal` for running text, `font-semibold` for labels and titles, `font-bold` for page titles, figures and the display. Stat values take the `figure` utility (rounded, tabular figures). Inline text links get the `link` utility; the first cell of a wide table gets `PINNED_CELL` from `components/ui/table.ts`.
- Manual task and goal entry stays quiet (DESIGN.md's Agents First Rule): `ManualEntry` in a page header, or a ghost `Popover` in a card header. Never lay an add form open on a page. `ManualEntry`'s Task/Goal radios share one name, so render it once per page.
- A panel that leads elsewhere rather than acts (Resume) is `Popover look="link"`, after a row's actions. The way back into an agent's session is `ResumeLink` or `ResumePopover` from `components/agent-sessions.tsx`; a `CopyButton` that sits beside others takes a `subject` ("session id") so screen readers can tell them apart.
- `cx` joins classes; it does not merge them. Pass a class that conflicts with a component's own and both apply, so add a prop or a variant instead.
- Charts are server-rendered spans placed by `lib/timeline.ts` fractions. Keep the maths in `lib` (with unit tests) and the layout in `components/charts`. Every diagram needs a text equivalent for screen readers, and state must not rely on colour alone.
- Text an agent wrote can be long and have no spaces (a repo path, an env var name). A button holding it, such as a decision's option, is `Button` size `choice`, which wraps within its container (`wrap-anywhere`, `max-w-full`); never put agent text in a `whitespace-nowrap` control without `truncate`. Popovers flip to the other edge of their trigger when the panel would leave the screen.
- Form controls are `w-full` by design and class order cannot override it. Size the wrapper (a grid column or a `div` with a width) instead of the control.
- Reuse the primitives before writing markup: `ActionButton`, `GoalField` (goal and parent pickers), `CopyField`, `FlowStat`, `GoalLink`, `segment` from `components/ui/segmented.ts`, `TH` and `PINNED_CELL` from `components/ui/table.ts`, and `Button`'s `pending` state.
- A card-like box on the ground is `Card`, or the `surface` utility (panel, with its lit top edge in dark), never a bare `bg-panel`. Empty space is `EmptyState`; its `art` (the `spot-boulder` and `spot-signal` illustrations) is for the rare empty state that is a moment (Decisions' All clear, the Agents page's No agents yet), never a working surface.
- Undo for frequent actions, confirm for rare ones (DESIGN.md's Undo or Confirm Rule). Drop, Done, lane moves and answers take a `notice` and an `undo` (the reverse transition) on `ActionButton` or `ActionForm`, shown in the workspace's one status region (`StatusRegion` in `components/ui/status-region.tsx`). Rare, hard-to-reverse actions (Revoke, Forget, Abandon, Remove, Mark achieved with open tasks, Mark answered) take a `confirm` message instead.
- One-click actions say what they did, naming the object ("Dropped “Read the thread”"), through `notice`; a form panel that closes on success (`closeOnSuccess`) reports the same way. Never rely on the row simply vanishing.
- A row that leaves when its action runs passes `exits` to the button and fades with `has-[[data-exit][data-pending]]`; pending buttons spin (`Button`'s `pending`).
- Popovers take focus when they open and open upward when there is no room below. A form panel gets a `title` and a `PopoverCancel`; a panel of one-click rows is `Popover menu` with `Button` size `menu`. The rare moves of a row (Release, Drop, Mark answered) live in its ghost `⋯` menu, named "More actions for …".
- Toolbar filters are `ToolbarSelect` capsules; form fields stay `Select`. A filter held in the URL is a `QueryFilter` (as `GoalFilter` and `StatusFilter` are). A search box is `SearchForm` (a pill with a clear button and the `/` shortcut); give it `suggestFor` to make it the suggestions combobox, whose options come from `suggest` in `server/domain/search.ts` and `lib/suggestions.ts`. Workspace pages are listed once, in `WORKSPACE_PAGES`.
- The Tasks page's layouts (Board, Table, Calendar, Map) share one set of filters (`lib/task-views.ts`); the non-board layouts read tasks through `browseTasks`, and their maths (sorting, the month grid, the map's tree) lives in `lib` with unit tests. Link to a status's tasks with `routes.tasksByStatus`.
- Tasks and documents open in a peek through the `@peek` parallel slot in `app/w/[slug]` (intercepting routes `(.)tasks/[id]` and `(.)documents/[id]`, wrapped in `Peek`), and as full pages at `/tasks/[id]` and `/documents/[id]`. Build both from one view (`TaskDetail`, `DocumentDetail`) with `headingLevel={2}` in the peek. Link to them with `Link` and `scroll={false}`; "Open as page" is a plain `<a>`, which is never intercepted. The slot's `[...rest]` page closes a peek on any other navigation.
- Selection is marked with `data-selected` plus `aria-current`, never colour alone (`DecisionKeys` for requests, `SELECTED_CARD` for board cards).
- Agents may run sub-agents (`agents.parent_agent_id`, one level deep): `createSubagent` for an agent's own, `createAgent` with `parentAgentId` for owners, and detected ones (`shares_parent_key`), which use their parent's token with a `Phean-Agent-Name` header, `?agent=`, or a per-call `actingAs` (added to every tool in `mcp/handler.ts`), and are found or made by `resolveNamedSubagent`. A name names one sub-agent per parent: `resolveNamedSubagent` reuses the parent's existing sub-agent of that name however it was made (oldest live first), and `issue` refuses a second live one, so `actingAs` always acts as the agent a handoff or a claim names. Requests they ask carry `viaAgentName`; show the asker with `askerName` and the app with `askedInApp`. Revoking an agent revokes its sub-agents; revoking a detected one refuses that name. List them nested under their parent.
- Pipelines (`docs/pipelines/PLAN.md`): the pure rules are `lib/pipelines.ts`, the services `domain/pipelines.ts`, the engine `domain/pipeline-engine.ts`. A run's stops are subtasks of the run's task, created only through the task services as the workspace's pipelines agent (`pipelineContext`, actor `system: true`, `agents.auth_kind = 'system'`, never listed or revoked); never write `tasks` for a pipeline directly, and never set `system` anywhere else. A task service that finishes, drops, releases, hands back or answers a task calls the engine hook in its transaction (`onTaskFinished`, `onRequestAnswered`, `onTasksCaptured`), skipped for the engine's own changes. Reaching a stop goes through the current-row unique key and finishing one through `settleRow`'s live-state guard, so each happens once. A person stop's decision is tagged `InputRequest.pipeline` and only its approvers may answer it. Changing a regular pipeline is its owner's or `pipeline:manage`'s; an agent's change is a proposal. Keep `skills/phean-pipelines/SKILL.md` in step with "Pipelines" in `guidance.ts` and the pipeline schemas (`tests/skills.test.ts` checks it).
- Keyboard shortcuts are listed in `components/keyboard-shortcuts.tsx` (the `?` legend); add a row there for any new one, and never bind a key while focus is in a field.
- Analytics is Google Analytics 4 through `track` and the `EVENTS` catalog in `src/lib/analytics.ts`, and `sendServerEvents` in `server/analytics.ts` for what agents do over MCP (from `onCommit`, never awaited). Every new user-facing surface or action adds its events to `EVENTS` and to the dictionary in [docs/ANALYTICS.md](docs/ANALYTICS.md) (`tests/analytics.test.ts` checks both). Params are enums, booleans, buckets (`countBucket`) and public slugs only: never a name, title, note, question, answer, URL from the app, search term, slug or id. People and workspaces are `analyticsHash` on the server. Page views carry the route pattern (`redactLocation`); a new route gets a case in the test's `ROUTE_CASES`. Nothing loads before the visitor accepts (`phean-consent`).
- "Decision" means an agent's request and nothing else: a goal waiting on a person is an approval, and the memory kind `decision` reads "Choice".

### Tests

- Tests run against in-memory PGlite through the real services and the real MCP handler. Add a case to `tests/isolation.test.ts` for anything that reads or writes tenant data, and to `tests/policy.test.ts` for any permission change.
- A database test seeds its own workspace with `seedWorkspace(db)` in `beforeEach` and never reads what another test wrote. `pnpm exec vitest run --sequence.shuffle` catches a test that does.
- UI tests in `e2e/` find things the way a person does: by role, label, and visible text. `card(page, title)` relies on `Card` rendering a `<section>` and `CardHeader` an `<h2>`. The diagrams expose `data-task`, `data-segment`, `data-end`, `data-now`, and `data-tick` for assertions a person makes by eye; keep them when you restyle.
- Specs share the seeded demo account through the `setup` project because sign-in is rate limited. Read-only specs use the seeded Globex workspace and its three weeks of history; a spec that writes creates its own account and workspace with `newWorkspace` (`e2e/support/accounts.ts`), so specs can run in parallel.
- Sign-up allows three per 10 seconds from one client. A spec signs up at most one person (`signUp` waits out the limit and retries when parallel specs hit it together); a second person is the demo account in its own browser context (`DEMO_SESSION`), and the spec undoes what it changed for them.
- Move between workspace tabs with `openTab` (`e2e/support/navigation.ts`), which waits for the new URL. Pages share controls (memory and search both have a search box), so acting before navigation finishes can hit the page being left.
- Every new page goes into `PAGES` in `e2e/quality.spec.ts` (axe and the 375px checks), or `BACKOFFICE_PAGES` for a backoffice page (visited as the seeded platform admin, `ADMIN_SESSION`), every new timetable into `TIMETABLES`, and every popover whose content matters into `PANELS` (axe scans skip a closed panel).
- The tab rail's counts are in the workspace layout, which client navigation keeps; after an agent changes something over MCP, load the page with `page.goto` before asserting on them.
