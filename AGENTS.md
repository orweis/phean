## Working on Phean

Read [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) first. The rules below are the ones that are easy to break.

### Commands

- `pnpm check` (typecheck, lint, tests) must pass before every commit. Run `pnpm build` too when touching routes, layouts, or anything imported at module load.
- `pnpm test:e2e` builds and runs the Playwright UI tests on port 3200 against `.data/e2e`. Run it after any UI change. It needs `pnpm exec playwright install chromium` once, and it reuses a server already listening on 3200, so stop a stale one after rebuilding. To rerun without rebuilding: `pnpm exec playwright test`.
- CI (`.github/workflows/ci.yml`) runs `pnpm check` and `pnpm test:e2e` on every pull request.
- Work that needs direct access the cloud session lacks (the Vercel dashboard or CLI, a store's token, production secrets) is spun off as a local session on the owner's machine with a self-contained prompt, rather than handed back as manual steps. Never paste tokens or secrets into a chat, a prompt, or the repository.
- `pnpm dev` and `pnpm db:seed` both use the on-disk PGlite database by default, and PGlite allows one process at a time. Stop the dev server before seeding.
- `PageProps<"/route">` and `LayoutProps<"/route">` are generated types. `pnpm typecheck` runs `next typegen` first, so a fresh checkout has them; a bare `tsc` will not.

### Where code goes

- Business rules live in `src/server/domain` as `service(schema, run)` functions, which validate their own input. Routes, server actions, and MCP tools are thin adapters that take the service itself; they never query the database themselves.
- Tenant scoping comes only from `Ctx`, which is built from a session or from the verified agent's row in `agents`. Every query on a tenant table filters through `inTenant(ctx, table)` or `tenantRow(ctx, table, id)`, and every insert sets `tenantId` from `ctx`. Never accept a tenant id or slug from tool input, and never from an OAuth token's claims: the token names only the agent (`agent_id`), and the row says which workspace it is in.
- An agent's bearer is an OAuth access token (the main path, verified by `verifyOAuthToken`, then `resolveOAuthAgent`) or a fixed `phn_` key (`authenticateAgentToken`). Every path that turns a credential into an agent goes through `resolvePrincipal` in `domain/agents.ts`, which reads the row through `liveAgent()` (`agent-liveness.ts`), so revoking, expiry and an approver leaving cut an agent off on its next request. A sub-agent is live only while its parent is, and its effective level is the lowest of its own, its parent's, and (for an OAuth agent) what its approver can grant now. Add any new token path there, never beside it.
- Agent levels are `read`, `write` and `admin`, the roles `agent_read`, `agent_write` and `agent_admin` in `policy.ts`. Fixed keys are Write and never expire; OAuth agents get a level and a lifetime from `AGENT_LIFETIME_DAYS` in the dialog, and there is no "never". People approve agents with `agent:connect` (Admin only with `agent:manage`; `grantableLevels` reads it from the matrix), and only owners and admins issue fixed keys with `agent:issue_key`. `agent:manage` means revoking others' agents and an Admin agent holds it; issuing keys and `member:manage` stay with people. A person may also revoke an agent they approved (`createdByUserId`), or a sub-agent of one; `canRevoke` in `agents.ts` is that rule for the service and the Agents page alike. An MCP tool for Admin agents only is `adminOnly`.
- Update services build their `set` with `patchOf`, so `undefined` means "leave it" and `null` means "clear it" everywhere, and throw `invalid` when nothing would change.
- Authorization is the matrix in `src/lib/permissions.ts` (plain data, so client-safe code such as `grantableLevels` reads the same table), enforced by `assertCan` in `src/server/domain/policy.ts`. Call `assertCan` in the service; do not scatter role checks in UI or adapters. `goal:decide` stays human-only.
- An MCP tool that is one service is `serviceTool({ name, title, description, service, key })` in `src/server/mcp/tools.ts`; use `defineTool` only when the tool adds links or formats text. Mark read-only tools `readOnly` and deleting tools `destructive`, and write descriptions for the agent that will read them.
- New workspace mutations are one `tenantAction(service, options)` line in `src/app/w/[slug]/actions.ts`, rendered with `ActionForm`, or `ActionButton` for a one-click post of fixed fields.
- Labels and colors for statuses, priorities, roles, and kinds come from the `{ label, tone }` tables in `src/lib/domain.ts`. Paths come from `routes` in `src/lib/routes.ts`. Field limits come from `LIMITS` and the slug rule from `WORKSPACE_SLUG_PATTERN`, for the schema and the form alike. Do not hard-code any of them.
- Dates are UTC calendar days through `src/lib/dates.ts` (`isoDayFromToday`, `daysBetween`, `isPastDue`), in the app, the scripts, and the tests.
- `src/lib` is client-safe and must not import from `src/server`.
- Agent sessions and questions are JSONB on `tasks`, shaped by `src/lib/agent-sessions.ts`. Change them inside `inTransaction` on a row read with `findTask(tx, id, { lock: true })`, so concurrent agents never drop each other's sessions. A session URL is checked with `isResumeUrl` in its schema and stored normalized; anything rendered as a link from agent input goes through `OutsideLink`, and only `webUrl` decides what is a web link. Never widen `RESUME_URL_SCHEMES` to schemes that run code (`javascript:`, `data:`, `file:`).
- A service that ends a task's run (complete, release, any status change except to in progress) closes its `inputRequest` with `closeOpenRequest()`, which archives it in `inputAnswers`, so no question outlives the work it was about and the Decisions page keeps its history.
- Links agents leave (`tasks.links`, `InputRequest.links`) are validated by `LinkInput` with `isResumeUrl` and stored normalized by `normalizeLinks`; render them with `TaskLinks`, which goes through `OutsideLink`.
- A task's operator is `claimed_by_agent_id` (an agent's claim) or `operator_user_id` (a person who took it), never both; `delegation` is the handover around them (`DELEGATION_STATES` in `lib/domain.ts`). Change them only through `claimTask`, `takeTask`, `handOffTask`, `cancelHandOff`, `releaseTask`, `completeTask` and `updateTask` in `tasks.ts`, which keep the two consistent; an agent must not change work another operator holds (`assertNotClaimedByOther`), unless it is being handed to it. Show them with `TaskMeta` and `DelegationBadge`.
- Subtasks are one level deep: `assertValidParent` in `tasks.ts` refuses a subtask as a parent and a task with subtasks as a child. `TaskView` carries `parentTitle`, `subtaskCount` and `subtasksDone` from `selectTaskViews`; build task lists from it, not from raw rows.
- `skills/phean-decisions/SKILL.md` is the installable skill for agents that ask people for decisions. Keep it in step with "Asking the human" in `src/server/mcp/guidance.ts` and with `AskInput`; `tests/skills.test.ts` checks its tool names, kinds, fields, limits, and its example request against the server.
- `skills/phean-handoffs/SKILL.md` teaches agents operators, delegation and handoffs. Keep it in step with "Operators and handoffs" in `guidance.ts`, `HandOffInput` and `DELEGATION_STATES`; `tests/skills.test.ts` checks its tool names, states, fields and its example handoff.
- `skills/phean-webhooks/SKILL.md` teaches bots to verify and handle webhooks. When signing, headers, limits, backoff or delivery reasons change in `src/server/webhooks`, update it; `tests/skills.test.ts` runs its Node and Python verifiers against `signPayload` and checks the limits it quotes.
- Webhooks hang off `recordEvents`: it records the acting agent's watches and queues `webhook_deliveries` in the caller's transaction, and wakes the dispatcher with `onCommit`. Log every change through `recordEvents` inside the service's `inTransaction`, never by inserting into `events` directly, or bots will not hear about it. Payloads carry the event, not the object, so put what a bot needs to act in the event's `data` (ids, `goalId`, `taskId`), never secrets.
- MCP is served at `/mcp` and at each workspace's own `/mcp/w/[slug]` (`routes.mcp(slug)`), because Cursor and VS Code keep one login per URL. The slug never chooses the tenant: the handler refuses any credential whose agent works elsewhere, a workspace URL's tokens carry it as their audience, and `customAccessTokenClaims` refuses one to an agent of another workspace.
- Anything that calls an agent-supplied URL goes through `assertWebhookUrlSafe` and `postSigned` in `src/server/webhooks`; never `fetch` one directly.
- A task's `status` is its kind; the board's lanes are the workspace's stages (`lib/workflow.ts`, saved per workspace by `saveWorkflow`). Read a task's lane with `stageOf(workflow, task)` and its name with `stageLabel`, never `TASK_STATUS_META` alone; in server components the workflow comes from `workspaceWorkflow(slug)` in `server/web.ts`. Any service that changes a task's status clears `stage` unless it keeps the kind. Charts stay per kind.
- Document bytes go through `blobStore(ctx)` in `server/storage/blobs.ts` (private Vercel Blob, or the database), never `@vercel/blob` directly, and are served only by `/w/[slug]/documents/[id]/file` after its access check. Render agent Markdown with `MarkdownView` (no raw HTML) and HTML documents as source only. `skills/phean-documents/SKILL.md` teaches agents documents; keep it in step with "Documents" in `guidance.ts` and with `AttachDocumentInput` (`tests/skills.test.ts` checks it).
- `answered` and `answered_elsewhere` are the only outcomes delivered to agents (`DELIVERED_OUTCOMES`); deliver them through `collectAnswers` so each answer arrives once.

### Database

- Change the schema in `src/server/db/schema`, then `pnpm db:generate` and commit the SQL in `drizzle/`. Migrations only move forward and run on every Vercel build, so keep them compatible with the previous release.
- Nothing may open the database at import time; `next build` runs without one. Use `getDb()` inside functions, or `lazyDb` where a handle must exist at module load. `auth` in `server/auth/auth.ts` is a lazy Proxy for the same reason (the OAuth provider writes its resource row when built): import it freely, but build a real instance only with `createAuth(db, baseUrl)`, as the tests and `auth.config.ts` do.

### UI

- [DESIGN.md](DESIGN.md) is the visual system; read its Do's and Don'ts before styling anything. The tokens live in `src/app/globals.css`, and keep the two in step when you change either.
- Tailwind's default palette is switched off (`--color-*: initial`). Use the token names (`ink`, `muted`, `panel`, `fill`, `rule`, `accent`, `on-accent`, `signal`, `dusk`, `late`, `wait`, `move`, `arrive`, `station-*`); `bg-blue-500` will not exist. Every token has a dark value under `@variant dark` in `globals.css`, so never write a `dark:` variant or a literal colour; check a new pair at 4.5:1 (text) or 3:1 (lines) in both appearances.
- The appearance (Light, Dark, or System) is the `phean-appearance` cookie, rendered as `<html data-appearance>` by the root layout through `getAppearance()` in `server/web.ts`; the custom `dark` variant keys on that attribute, with System following `prefers-color-scheme`. Anything that must match it on the server (a colour in an image, a meta) reads `getAppearance()`, and `lib/appearance.ts` holds the values the picker and the layout share. Never read `matchMedia` for it in a component.
- Violet (`accent`) is the brand: one or two filled primary buttons per view, and `tinted` for an action repeated on every row. Ember (`signal`) is the boulder, the counts on the tab rail, the inbox, and the one call to action on a dusk band. Red is only for lateness, danger, and the now line. Status hues come from the tone tables and `components/charts/stations.ts`, never picked in a component.
- Liquid Glass belongs to the functional layer only: `glass-bar` for the sticky header and `glass-float` for menus, popovers and sheets. Never make a card, lane or chart glass. Controls are capsules (`rounded-full`); cards are `rounded-lg`.
- Three weights only: `font-normal` for running text, `font-semibold` for labels and titles, `font-bold` for page titles, figures and the display. Stat values take the `figure` utility (rounded, tabular figures). Inline text links get the `link` utility; the first cell of a wide table gets `PINNED_CELL` from `components/ui/table.ts`.
- Manual task and goal entry stays quiet (DESIGN.md's Agents First Rule): `ManualEntry` in a page header, or a ghost `Popover` in a card header. Never lay an add form open on a page. `ManualEntry`'s Task/Goal radios share one name, so render it once per page.
- A panel that leads elsewhere rather than acts (Resume) is `Popover look="link"`, after a row's actions. The way back into an agent's session is `ResumeLink` or `ResumePopover` from `components/agent-sessions.tsx`; a `CopyButton` that sits beside others takes a `subject` ("session id") so screen readers can tell them apart.
- `cx` joins classes; it does not merge them. Pass a class that conflicts with a component's own and both apply, so add a prop or a variant instead.
- Charts are server-rendered spans placed by `lib/timeline.ts` fractions. Keep the maths in `lib` (with unit tests) and the layout in `components/charts`. Every diagram needs a text equivalent for screen readers, and state must not rely on colour alone.
- Form controls are `w-full` by design and class order cannot override it. Size the wrapper (a grid column or a `div` with a width) instead of the control.
- Reuse the primitives before writing markup: `ActionButton`, `GoalField` (goal and parent pickers), `CopyField`, `FlowStat`, `GoalLink`, `segment` from `components/ui/segmented.ts`, `TH` and `PINNED_CELL` from `components/ui/table.ts`, and `Button`'s `pending` state.
- Undo for frequent actions, confirm for rare ones (DESIGN.md's Undo or Confirm Rule). Drop, Done, lane moves and answers take a `notice` and an `undo` (the reverse transition) on `ActionButton` or `ActionForm`, shown in the workspace's one status region (`StatusRegion` in `components/ui/status-region.tsx`). Rare, hard-to-reverse actions (Revoke, Forget, Abandon, Remove, Mark achieved with open tasks, Mark answered) take a `confirm` message instead.
- One-click actions say what they did, naming the object ("Dropped “Read the thread”"), through `notice`; a form panel that closes on success (`closeOnSuccess`) reports the same way. Never rely on the row simply vanishing.
- A row that leaves when its action runs passes `exits` to the button and fades with `has-[[data-exit][data-pending]]`; pending buttons spin (`Button`'s `pending`).
- Popovers take focus when they open and open upward when there is no room below. A form panel gets a `title` and a `PopoverCancel`; a panel of one-click rows is `Popover menu` with `Button` size `menu`. The rare moves of a row (Release, Drop, Mark answered) live in its ghost `⋯` menu, named "More actions for …".
- Toolbar filters are `ToolbarSelect` capsules; form fields stay `Select`. A filter held in the URL is a `QueryFilter` (as `GoalFilter` and `StatusFilter` are). A search box is `SearchForm` (a pill with a clear button and the `/` shortcut); give it `suggestFor` to make it the suggestions combobox, whose options come from `suggest` in `server/domain/search.ts` and `lib/suggestions.ts`. Workspace pages are listed once, in `WORKSPACE_PAGES`.
- The Tasks page's layouts (Board, Table, Calendar, Map) share one set of filters (`lib/task-views.ts`); the non-board layouts read tasks through `browseTasks`, and their maths (sorting, the month grid, the map's tree) lives in `lib` with unit tests. Link to a status's tasks with `routes.tasksByStatus`.
- Tasks and documents open in a peek through the `@peek` parallel slot in `app/w/[slug]` (intercepting routes `(.)tasks/[id]` and `(.)documents/[id]`, wrapped in `Peek`), and as full pages at `/tasks/[id]` and `/documents/[id]`. Build both from one view (`TaskDetail`, `DocumentDetail`) with `headingLevel={2}` in the peek. Link to them with `Link` and `scroll={false}`; "Open as page" is a plain `<a>`, which is never intercepted. The slot's `[...rest]` page closes a peek on any other navigation.
- Selection is marked with `data-selected` plus `aria-current`, never colour alone (`DecisionKeys` for requests, `SELECTED_CARD` for board cards).
- Agents may run sub-agents (`agents.parent_agent_id`, one level deep): `createSubagent` for an agent's own, `createAgent` with `parentAgentId` for owners, and detected ones (`shares_parent_key`), which use their parent's token with a `Phean-Agent-Name` header, `?agent=`, or a per-call `actingAs` (added to every tool in `mcp/handler.ts`), and are found or made by `resolveNamedSubagent`. A name names one sub-agent per parent: `resolveNamedSubagent` reuses the parent's existing sub-agent of that name however it was made (oldest live first), and `issue` refuses a second live one, so `actingAs` always acts as the agent a handoff or a claim names. Requests they ask carry `viaAgentName`; show the asker with `askerName` and the app with `askedInApp`. Revoking an agent revokes its sub-agents; revoking a detected one refuses that name. List them nested under their parent.
- Keyboard shortcuts are listed in `components/keyboard-shortcuts.tsx` (the `?` legend); add a row there for any new one, and never bind a key while focus is in a field.
- "Decision" means an agent's request and nothing else: a goal waiting on a person is an approval, and the memory kind `decision` reads "Choice".

### Tests

- Tests run against in-memory PGlite through the real services and the real MCP handler. Add a case to `tests/isolation.test.ts` for anything that reads or writes tenant data, and to `tests/policy.test.ts` for any permission change.
- A database test seeds its own workspace with `seedWorkspace(db)` in `beforeEach` and never reads what another test wrote. `pnpm exec vitest run --sequence.shuffle` catches a test that does.
- UI tests in `e2e/` find things the way a person does: by role, label, and visible text. `card(page, title)` relies on `Card` rendering a `<section>` and `CardHeader` an `<h2>`. The diagrams expose `data-task`, `data-segment`, `data-end`, `data-now`, and `data-tick` for assertions a person makes by eye; keep them when you restyle.
- Specs share the seeded demo account through the `setup` project because sign-in is rate limited. Read-only specs use the seeded Globex workspace and its three weeks of history; a spec that writes creates its own account and workspace with `newWorkspace` (`e2e/support/accounts.ts`), so specs can run in parallel.
- Sign-up allows three per 10 seconds from one client. A spec signs up at most one person (`signUp` waits out the limit and retries when parallel specs hit it together); a second person is the demo account in its own browser context (`DEMO_SESSION`), and the spec undoes what it changed for them.
- Move between workspace tabs with `openTab` (`e2e/support/navigation.ts`), which waits for the new URL. Pages share controls (memory and search both have a search box), so acting before navigation finishes can hit the page being left.
- Every new page goes into `PAGES` in `e2e/quality.spec.ts` (axe and the 375px checks), every new timetable into `TIMETABLES`, and every popover whose content matters into `PANELS` (axe scans skip a closed panel).
- The tab rail's counts are in the workspace layout, which client navigation keeps; after an agent changes something over MCP, load the page with `page.goto` before asserting on them.
